## Read-only findings

Server operations verify users using `auth.getUser`, then query membership with both the requested tenant and verified user ID. Mutation roles are checked before writes. Location and equipment parents are scoped to tenant and customer. Query chains retain tenant predicates. Error messages do not disclose database details. Auth callback redirects only to fixed internal destinations. Request clients use publishable keys and user cookies; no application service-role client or application logging of credentials/records was found. Protected server rendering reads request cookies; no shared application data cache is configured. Next Server Actions supply their standard origin protections; no custom permissive origin allowlist is configured.

Migration inspection found RLS on all foundation tables, a fixed empty search path on security-definer functions, authenticated-only execution of the membership helper, composite tenant/parent foreign keys, no membership provisioning grants to ordinary users, and trigger-written audit events without ordinary insert/update grants. Audit events store record identity and action without copies of personal data. Demo seed and test data are fictional. Technician/viewer roles intentionally read tenant records and cannot mutate; assignment-scoped technician access remains future work.

Finding Q1, statically remediated: entity UPDATE grants originally included identity, tenant and timestamp columns. A user authorized in tenants A and B could move a bare customer from A to B by directly updating `tenant_id`, changing its workspace and audit attribution. Reproduction: provision dispatcher membership in both demo tenants; authenticate as that user; update a customer with no child references from A to B through SQL or PostgREST. Expected: immutable record/tenant identity. The Architect replaced broad UPDATE grants with column-specific business-field grants that exclude tenant, ID, parent references and timestamps. Quality reviewed the fix and SQL regression covering privilege metadata, multi-tenant reassignment denial, ID/parent denial and allowed business updates. Static remediation is approved; execution of the database regression is still blocked by unavailable database tooling.

Frontend inspection found labeled native inputs, required/max-length constraints, server validation, live success/error announcements, pending form disabling, role-based mutation controls, loading and error boundaries, empty customer/location/equipment states, and customer detail forms whose names match backend contracts. No additional contract mismatch was found.

## Running browser coverage

Start an unconfigured local app, set `E2E_CHROMIUM_PATH` to an installed Chromium executable if needed, then run `node node_modules/@playwright/test/cli.js test`. `E2E_BASE_URL` overrides the default `http://127.0.0.1:3000`. For disposable authenticated tests use `E2E_AUTHENTICATED=1`, `E2E_EMAIL`, `E2E_PASSWORD`, `E2E_TENANT_ID`, `E2E_FOREIGN_TENANT_ID`, `E2E_TECHNICIAN_EMAIL`, and `E2E_TECHNICIAN_PASSWORD` in the process environment only. The first account must be owner/admin of the first tenant and have no membership in the foreign tenant. Never commit credential values or enable artifacts for authenticated tests.
