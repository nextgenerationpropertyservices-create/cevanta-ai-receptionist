## Supported boundaries

- Invitation-only entry to an already provisioned tenant; no domain-based claim or public tenant creation. Initial owner/ownership changes use separately scoped trusted provisioning. Owner-only staff invitations and no owner-role escalation are reasonable proposed limits, pending Morgan's recorded decision.
- A random 256-bit token is only an invitation locator. Verified authenticated identity plus trusted confirmed email, current invitation state and intended tenant/role are independently required. Body/user_metadata authority is rejected. Differing existing membership does not get promoted; accepted invitations do not recreate removed/demoted access. Accept/revoke and membership/audit changes must be atomic.
- Current membership/operation-specific role and tenant-safe parents remain mandatory inside elevated RPCs and server workflows. RLS is defense in depth, not protection against a definer owner's omitted predicates. No ordinary app service-role design or direct client membership/config writes.
- Owner/admin configuration access, dispatcher operational projection and technician/viewer minimal capabilities are distinct. Sensitive escalation destinations, invitation details, secret references and readiness diagnostics stay out of broader projections. Existing CRM/jobs/calendar/M5 permissions continue independently of incomplete setup.
- Configuration and readiness are derived from saved backend data/trusted evidence. Resume navigation is not completion authority. Matching revision/check policy/expiry are necessary for verified evidence; booking remains blocked and release not evaluated. Saved hours/preferences/contacts do not prove availability, contact verification, delivery or live integration.
- Configuration commands use strict inputs, current authorization, expected versions, durable actor-scoped receipts and atomic audit/config-revision changes. Authorized exact replay returns original minimal result without new mutations or domain revalidation, and never substitutes for a fresh current detail read.

## Required clarifications before implementation

These are specification gaps, not reproduced vulnerabilities. No runtime exploit severity is claimed.

1. **Trusted email and recipient identity.** Specify the exact server and database source of confirmed account email, confirmation requirement, canonical comparison and behavior during concurrent account-email change. auth.uid() alone does not verify the invitation recipient. A definer RPC must not rely on an untrusted email argument or stale/mutable user_metadata; direct RPC access must enforce the same rule as the server. Define invited account signup/verification/return routing without exposing private invite details before authentication. No Gmail dot/plus transformations; canonicalization must match issuance and redemption. Define whether accepted replay still requires original email binding after a legitimate email change; do not let implementers choose independently.
2. **Token lifecycle and request handling.** Pin format, byte length, digest algorithm/location and token-generation authority, expiry and trusted evaluation instant. Never expose plaintext via management results, receipt/audit, telemetry, URL/access logs, browser history, referer, screenshots or exception traces. Define how the acceptance page consumes and removes sensitive URL material, avoids third-party content/referral leakage and preserves secure continuation through login; fragment versus other transport needs an actual reviewed flow. No token-bearing receipt input/log projection; if token participates in canonical retry identity, store only an approved digest. Outbox encryption, key access/rotation, approved delivery and failure/retry policy require a separate reviewed contract. Forged/expired tokens need bounded processing and admission/rate controls without token/account enumeration.
3. **One invitation/membership transaction sequence.** Atlas explicitly defers invite provisioning lock compatibility. Publish exact order for creation, acceptance, revocation, membership removal/role change and configuration/M5 commands, including invitation, tenant, existing or absent membership, request and uniqueness locks. Define fresh snapshots after waits and concurrent accept/accept, accept/revoke, accept/remove/demote, and two invitations for one recipient/tenant. Locking an existing membership cannot serialize an absent row: unique tenant/user enforcement plus reviewed conflict recovery is required. Define lost-response retry, changed request/token, accepted-token expiry and the point at which permission changes take effect. Never recover a collision by silently changing role or resetting accepted status.
4. **Issuer reauthorization and invitations after issuer loss.** Creation/revocation require current owner checks inside RPC. Record the policy for pending invitations when their issuer loses membership/ownership or the tenant is disabled. An invite can remain valid only under an explicitly accepted tenant delegation policy, not by accident. Define duplicate pending invitations, reissue/revoke behavior and minimal owner-management error/result projections. Initial owner invitations must be unmistakably restricted to trusted provisioning.
5. **Projection and resume precision.** Resolve SaveResumeStep owner/admin-only configuration guard versus “current user's own resume” wording. State permitted roles and deny another user's resume even within the same tenant. Separate public/private storage or column grants so dispatcher/technician/viewer cannot fetch restricted fields directly: row RLS does not hide columns. A security-invoker view cannot safely expose selected private fields if its required underlying grants also expose the whole table. Publish exact schema/view/RPC grants and result fields, including contact_email/phone, actor identifiers, readiness references, counts and reason codes. Bound every array/string/error code; specify exception interval/request limits as well as weekly ones.
6. **Version, readiness and shared timezone authority.** Choose the single name/trade/timezone source before migrations. Specify aggregate expected-version versus shared config_revision, no-op save behavior, receipt retention/version evolution and all updates that invalidate evidence, including existing settings commands. Read models need a consistent revision/data snapshot; stale checks must not mark newer configuration verified. Trusted readiness creation/refresh roles and policy are separate from owner/client writes. Evidence reference and failure codes must never expose destinations, keys, provider account identifiers or private logs. Clarify manual_workspace_state evidence scope so schema reachability or owner observation does not imply all-role/full-journey acceptance.
