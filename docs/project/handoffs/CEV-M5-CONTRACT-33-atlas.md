## Proposed minimal tables and contracts

1. **internal_estimate_drafts**: `id uuid` primary key; `tenant_id uuid`; `submission_id uuid`; `customer_id uuid` required in the recommended customer-anchored variant; optional `job_id`, `service_location_id`; bounded `title` (1–160 trimmed characters) and `scope_description` (1–4000); `status` restricted to literal `draft`; positive integer `version`, initially1; server-generated created/updated timestamps and verified creator/updater references. Unique `(tenant_id,id)` and `(tenant_id,submission_id)`. No sent/accepted/declined/paid/expired states, amounts, currency, tax flags, zero totals, terms, attachment/signature/payment references or automated effects. Draft-only status is a compatibility label rather than a customer commitment; no cancellation/delete command in the smallest slice unless explicitly added to scope.
2. **internal_estimate_followups**: tenant-owned UUID and estimate reference, creation token unique within tenant, `due_on date`, bounded internal note (0–2000), status scheduled/completed/cancelled, positive integer version, server timestamps/actors. Completion time/actor present only for completed status; terminal rows are retained. Create/reschedule/update note while scheduled; complete or cancel from scheduled; repeated identical operation replays original result. Completed/cancelled records are immutable; another follow-up is a new scheduled record. Recommend at most one active scheduled follow-up per estimate through a partial unique constraint/index, with history retained. Multiple active tasks and assignees deferred until explicitly required. Follow-up is an office task, never a provider job or customer message.
3. **Private mutation receipt**, if all commands promise replay: UUID request identity, tenant/verified actor/command scope, estimate or follow-up target, canonical validated-input digest and minimal committed result/reference/version. Unique `(tenant_id,actor_user_id,command,request_id)`; direct client reads/writes denied. Receipts and business/audit changes commit together. No raw notes/PII/financial payload in receipt or logs. Exact hashing canonicalization, retained result shape and retention require Blake/Quinn review. Creation's tenant/submission identity is still globally unique; do not use actor-scoped receipts to allow duplicate creation. This receipt is optional only if edit contracts explicitly promise conflict-safe at-most-once updates rather than replay; choose the guarantee before implementing.

**No line table or revision-snapshot table in the recommended non-monetary minimum.** A bounded scope description captures planning without inventing quantity/unit/prices. Optimistic `version` is a concurrency token, not a full immutable content revision or an issued estimate version. If structured work-scope rows are actually needed, add tenant/estimate/id/position/description plus optional equipment reference after review, with no disguised price defaults. ## Relationship invariants and deferred links

- Every child has a tenant-aware foreign key to its estimate; all draft parents must be in that tenant. Identity, tenant, creation token and chosen parent links cannot be changed by ordinary update commands. Define a separate explicit relinking workflow later if required.
- Recommended minimum requires a known customer; job is optional. When job is selected, its customer must match and be non-null. Prefer a composite target `(tenant_id,customer_id,id)` on jobs to enforce the estimate/job/customer chain; introduced through a new additive migration, not rewriting migration003. Reject customerless jobs rather than silently updating them. Job immutable parent columns already support a stable chain.
- Optional location requires the same customer using the existing unique `(tenant_id,customer_id,id)` location target. A selected job's non-null location must agree with the draft location; if the job has a location, derive that link or reject contradictory client input. If job.location is null, separately selected same-customer location is permitted only under the reviewed selection rule.
- **Lead:** no independently writable lead FK in the minimal draft. Display job.lead_id as origin when available; do not treat it as the draft's recipient anchor or automatically change the lead. Current lead.customer_id is editable, so a stable direct lead/customer invariant would require a reviewed snapshot/origin semantic or enforcement across lead updates. Lead-only drafts and independently selected lead/job combinations remain deferred decisions, not guessed links.
- **Equipment:** defer a stored equipment link in the minimal description-only variant. If needed in structured scope rows, require an explicit linked location and composite `(tenant_id,service_location_id,equipment_id)` target; extend equipment with the necessary unique target through additive migration. Enforce equality with the draft's linked location in the database. Mere same-tenant existence is insufficient. Do not use equipment/customer links to grant access.
- **Calendar:** estimates do not require appointment links. No save/completion changes job status, creates an appointment or books a resource. Draft follow-up is independent of job scheduled_date, appointment timestamps and lead.follow_up_date.
- Protect historical record identity; no ON DELETE CASCADE from CRM/job/member deletion into drafts/follow-up/history. Actors must be derived from authenticated identity, never form input; actor retention after account removal needs a reviewed nullable/reference policy rather than blocking legitimate provisioning or deleting business history.

No ordinary direct INSERT/UPDATE/DELETE grants if those would bypass expected-version/idempotency/aggregate invariants. Mutations go through narrowly defined reviewed transactional RPCs. Prefer an execution-role design subject to RLS where feasible; if SECURITY DEFINER is needed to bridge revoked table grants, its owner may bypass RLS, so it must independently check auth.uid(), current tenant membership and allowed office role inside every function. Never treat RLS as automatically protecting a definer function. No ordinary app service-role client; function is not a generic arbitrary SQL/write gateway.

Authorized RPCs must not allow technician/viewer writes even when called directly, and no command may edit identities/generated timestamps/creator/parent links. Reads through helper views must preserve caller isolation; private receipts are not browser-accessible. Bind command permissions/guards in database and server with independent tests. ## Command and result boundaries

- `CreateDraft`: workspace/tenant selector, submission UUID, required approved customer anchor, optional approved job/location, title and scope. Reject unknown protected fields; derive actor and version1. Parent validation, draft insert, receipt and audit commit atomically. Same creation identity/same canonical payload returns original committed draft; changed payload under same token rejects as request-conflict, not overwrite.
- `UpdateDraft`: target UUID, expectedVersion, operation request UUID, mutable title/scope only. Lock/check current row and office membership, compare version, write and increment exactly once. Parent identities immutable. Return saved identity/version only after commit.
- `CreateFollowup`, `RescheduleFollowup`, `CompleteFollowup`, `CancelFollowup`: target and expected version where existing, operation UUID, approved date/note fields. Lock estimate first then follow-up consistently; enforce active-row uniqueness/state/version and atomic audit/receipt. Changing follow-up does not silently overwrite estimate content. Follow-up versions are separate; parent locks enforce visibility/existence and active-count rules. All commands acquire locks in the same order to avoid competing create/update races.
- Result union: saved (id/version), replayed (original committed id/version), validation_error (safe field issue), conflict (revision/request/active-followup), unavailable (missing/denied without foreign-record detail), retryable_failure. Server rechecks verified user/member; database independently enforces office permission. A replay does not return the newest content or authorize access for a removed member; reauthorize before reading any receipt. UI must preserve input on conflict and obtain current authorized state.
- Metadata audits remain atomic per changed business row and receipt semantics prevent duplicate change/audit on replay. Existing audit action model records INSERT/UPDATE/DELETE, not semantic command events; do not claim it records completed/cancelled meaning unless a separately reviewed event model is added. A rolled-back audit means no saved result. Follow-up terminal actor/time and state are structured protected business metadata, not spoofable form fields.

## Due-date semantics

Recommend manual date-only office follow-up: store strict valid `YYYY-MM-DD` as PostgreSQL date, no implicit execution hour or scheduler. Due today/overdue are read-time derived only for scheduled records against the current date in an approved valid tenant IANA timezone from trusted server time; completed/cancelled are not overdue. Return `workspaceToday` and timezone with list results so UI/backend agree, and recompute across midnight. Existing tenant timezone is editable and direct DB validation is loose; if using it, validate at read/command boundary and define unavailable/error behavior for invalid values, never fallback silently to UTC/browser time. Changing timezone can change derived labels but not due_on. No restriction against historical due dates assumed; an office can record overdue work unless owner decides otherwise. Owner/review must confirm date-only/current-workspace-date semantics before implementation; exact reminder instants are outside this slice.
