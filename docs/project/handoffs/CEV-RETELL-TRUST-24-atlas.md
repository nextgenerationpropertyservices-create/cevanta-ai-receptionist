## Approved boundary design

1. **Event kind and scope.** Initial adapter accepts only authenticated, schema-validated lifecycle `call_analyzed` envelopes with `event` and `call`. Reject unsupported event kinds before operational processing. The observed UI label maps conceptually to this documented kind; actual delivery remains unobserved. Post-call analysis cannot provide a mid-call booking confirmation. Treat appointment extraction as a request needing verification/office confirmation; it may later feed an independently reviewed booking workflow. Custom-function requests require a separate adapter and invocation identity, not reuse of this lifecycle contract. [Retell webhook overview](https://docs.retellai.com/features/webhook-overview)

2. **Version policy.** Distinguish provider agent configuration revision, extraction configuration revision and internal adapter/schema version. Editor V3 is not proof of the delivered agent revision, a provider webhook-schema version or published state. Do not invent a provider schema-version field. Pin a reviewed internal version, expected event/schema and extraction mapping; retain observed provider agent revision when actually supplied, otherwise explicit unavailable state. Unknown changed shapes or unsupported agent/extraction revisions go to rejection/quarantine for review, without effects. Exact accepted revision set and optional-field compatibility rules must be documented before an adapter ships.

3. **Authentication and routing.** Verify original signed body and signature using the provider's documented procedure and pinned implementation before trusting event contents. Assign the ingress connection and key/account association from private server configuration. Then bind authenticated agent identity to one enabled server-owned tenant route under that connection; reject wrong/unknown agents, disabled, ambiguous or mismatched routes. Do not require an invented payload account ID: account association can derive from the verified configured credential context. Caller/extracted tenant IDs, phone numbers, metadata and unauthenticated agent IDs have no routing authority. A generic webhook URL or client/config lookup is not authentication. Revalidate routing before durable effects; tenant/calendar destinations must derive from that same route. Until original bytes/header preservation and correct verification at Make are demonstrated, require a separate reviewed verifier ingress boundary before trusting Make. Do not repoint any existing receiver under this task. [Retell signature verification](https://docs.retellai.com/features/secure-webhook)

4. **Time semantics.** Keep trusted ingress `receivedAt`, authenticated signature delivery time, provider call start/end, any actually provided event-occurrence time, `verifiedAt` and trusted `evaluatedAt` distinct. Unknown event occurrence is unavailable; do not substitute call end and label it event occurrence. Signed delivery freshness does not mean the call itself is recent. Capture evaluatedAt once per validation attempt from approved execution infrastructure, never payload fields or mapped caller now. A Make current-time expression is a candidate only: approve exact UTC serialization/evaluation timing through isolated tests before use. Missing/invalid clock rejects. Revalidate future interval and availability immediately before reservation after queue delay/retry. Define allowed skew and stale-business-event policy explicitly; do not infer them from the observed5-second webhook timeout or documentation's generic timeout/retry description. [Make time functions](https://help.make.com/date-and-time-functions)

5. **Datetime and intent.** The observed labels are Appointment Requested (Yes/No), Preferred Appointment Date (Text), Preferred Appointment Time (Text), Requested Appointment Datetime (Text), and sms_consent (Yes/No), all allowing empty values. They are display/configuration labels, not proven JSON keys or Make paths. No format example was configured. Do not map them to fictional requestedAt fields by assumption. Confirm actual JSON serialization/types/path/missing-null behavior with safe evidence. Strict normalization accepts a real explicit-offset RFC3339 instant only, rejects missing, impossible, relative/free-text, offsetless, unknown-offset and ambiguous values, preserves canonical UTC and requires actual Boolean true intent. Never coerce yes/no strings or repair dates with defaults. Nonconforming extraction remains pending clarification; local-time/DST conversion needs a separately reviewed timezone-provenance and caller-confirmation rule. Approved duration remains trusted60-minute policy outside caller control; a supplied duration must match, and absent provider duration is not evidence of a provider-issued value. SMS consent is independent: only explicit verified true can permit a later separately authorized messaging workflow; no date result grants consent. [Retell extraction](https://docs.retellai.com/features/post-call-analysis-overview)

6. **Event identity versus operation identity.** For this restricted lifecycle projection, a candidate derived receipt identity is authenticated connection + authenticated agent + call ID + event kind, scoped to routed tenant. It is derived, not a provider-issued event ID. Establish retry stability and repeated-analysis behavior before adopting it. Same identity with changed normalized content requires an explicit conflict/revision policy, not a new side effect or silent overwrite. Provider call ID alone, delivery signature timestamp, Make execution ID and editor revision do not deduplicate booking intent. A booking operation gets a separate durable trusted identity; retries reuse it, while authorized reschedules require a distinct revision. Existing mandatory providerEventId ports need a separately reviewed compatibility change to represent derived identity honestly. No receipt store or dedupe implementation is established by this review.

7. **Outcome separation.** Transport receipt/authenticity, routed analysis, date validation, appointment request, availability, reservation and authoritative booking confirmation are separate states. Existing `{valid:true, starts_at_utc, ends_at_utc}` means only date validation passed. Failure requires Boolean false/reason and no usable timestamps. Initial normalized request can be pending review, rejected or clarification-required; it cannot be booked. A future booking contract must distinguish pending, confirmed, conflict, failed and unknown/reconciling with durable operation and provider/internal references. Caller/operator success requires committed authoritative confirmation, not analysis yes/no, a calendar availability check, queued Make execution, SMS API acceptance or a timed-out write. Unknown write outcome must reconcile the same operation before retry. Post-call request processing cannot retroactively promise confirmation during a completed call.
