## Password recovery: reviewed architecture requirements

No database migration or membership access is needed. Keep recovery separate from invitations and signup. Existing trusted provisioning remains unchanged.

- Request action accepts only a validated email. Call Supabase recovery using the publishable-key client and a fixed recovery URL built from validated trusted server configuration. Do not derive external origins from form input, Host, forwarded headers or a free next parameter. Never log addresses, passwords, token hashes, codes or full URLs.
- Return the same success message for a valid email regardless of account existence. Invalid syntax can receive a validation error. Rate-limited/unavailable messages must not reveal whether the account exists. Supabase throttling is required; do not implement an unbounded email sender.
- Use a dedicated recovery confirmation path, with a fixed /reset-password destination. Follow the installed Supabase SDK and documented recovery flow. For a token-hash email template, explicitly verify type=recovery with Supabase. For PKCE, enforce the SDK's recovery flow and code verifier. Never trust a caller-supplied type/next flag as evidence that the token was accepted.
- Password update must have a server-verified current user and successful provider-backed recovery context. A recovery query parameter alone is insufficient. If the UI allows an already signed-in user to change their own password, describe and test that behavior explicitly as an authenticated self-change rather than implying that a recovery link was verified. Never permit account selection from a posted email/user ID.
- Preserve the existing sign-in callback behavior; a separate recovery endpoint avoids turning arbitrary OAuth/login callbacks into recovery pages. A plain normal session must not show a misleading 'recovery link verified' state.
- Validate password and confirmation server-side; choose limits compatible with the configured Supabase password rules. Do not invent a new commercial/security policy if configured rules suffice. Bound input length, keep password whitespace semantics intact, reject mismatch, and display provider failure safely.
- Confirm provider success before showing success. Specify session behavior explicitly; recommended safe flow signs out the current browser session after successful reset and returns to sign-in. Do not claim that all other sessions were revoked without provider evidence.
- Required negative checks: malformed/expired/reused tokens, login token sent to recovery endpoint, missing recovery evidence, unauthenticated update, altered destination/origin, password mismatch, provider rejection/transport failure, and log redaction. Existing auth/membership checks must continue to pass.
- Access dependency: actual email delivery requires development Auth redirect allowlist, enabled email/password provider and working mail delivery. A token-hash approach also requires the corresponding recovery email template. Prepare code/tests first; never send unsolicited recovery email to a real owner identity as a test.

## Recovery contract clarification for immediate implementation

Approved simple variant: the dedicated /auth/recovery endpoint accepts token_hash and calls auth.verifyOtp({ token_hash, type: 'recovery' }). Provider success establishes a session and redirects only to /reset-password. Provider failure redirects to a fixed safe failure page. This variant requires the matching development recovery email template and redirect allowlist; it must be documented as an external acceptance prerequisite.

The update action may accept an existing server-verified authenticated session and change only that same user's password using auth.updateUser({password}). This is an authenticated self-change as well as the destination of successful recovery. It is safe without a new custom recovery-marker mechanism, provided UI copy never claims that an ordinary session proves a recovery link was verified. Unauthenticated requests fail; posted account IDs/emails are never used to select the account being changed. The reset page can use getUser to decide whether to show the form, with safe signed-out/expired instructions. This resolves the earlier recovery-context requirement without unnecessary new infrastructure: provider token verification protects the recovery entry, verified current-user identity protects the self-change operation.

Request action uses configured trusted APP_ORIGIN (or an equivalent validated dedicated server origin variable) to construct the fixed recovery redirect. Configuration helper/example/docs get one explicit owner. Exports remain requestPasswordRecovery(previous: ActionState, form: FormData): Promise<ActionState> and updateRecoveredPassword(previous: ActionState, form: FormData): Promise<ActionState>. Use form email for the request, password and confirmPassword for update. Return generic request success and safe update errors; never include provider payloads in ActionState. After confirmed update, sign out the current session and send the user to fixed /sign-in?reset=success only if sign-out succeeds; a sign-out failure must report an honest next action rather than claiming the session was ended.
