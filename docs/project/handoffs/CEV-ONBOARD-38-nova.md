## UX fit

Invitation-based entry is clear and safer than allowing arbitrary tenant claiming. Before verified identity, the acceptance page can ask the recipient to sign in/create and verify the intended account through the approved Auth flow; it must not display tenant/email details gleaned from a token. After committed acceptance, setup/dashboard entry is authoritative. A safe Already joined path uses ordinary authorized workspace entry, not a perpetual invitation token. Generic unavailable can explain that the invitation cannot be used and offer normal sign-in or contact-the-inviter guidance without identifying expired/wrong-recipient/revoked records. membership_conflict must not offer a role override. Delivery unknown is not Invitation sent; owner-management copy must distinguish created, delivery pending, confirmed and uncertain/failed according to approved evidence.

Owner/admin guided sequence can use business profile → services → hours/exceptions → request rules → escalation contacts → integrations → readiness review. First access is separate from business configuration. Save each step through actual commands, allow back/edit/resume from saved data and make pending/save/error state explicit. resume_step is navigation only, not completion. If a saved resume destination becomes unavailable or the flow changes, select a safe valid editable step; never treat old resume data as authority. Exact replay must refresh current authorized data rather than using its original config revision as current.

Progress should report named configuration steps derived from backend state; avoid a single percentage that counts provider-blocked steps as either client failure or live readiness. Show incomplete/blocked/error with text and specific next action. Missing business fields need a form link; platform-owned checks need a safe operator/support explanation. Services/hours/booking preferences are configuration, not live capacity or a reserved slot. Request-only copy should say Requests need office review. Saved escalation contacts do not imply verified delivery, emergency response or a human acknowledgement.

Readiness summary must distinguish Configuration incomplete/complete/invalid, Manual workspace usable/blocked, per-integration disabled/unconfigured/awaiting verification/verified/degraded, Booking blocked and Release not evaluated. No overall Ready/Go live button or success banner that combines these. A verified integration is still not booking authorization. checked_at/expires_at and configuration revision allow stale evidence to become awaiting verification. No provider call or write occurs when the user runs the pure readiness check.

Incomplete onboarding is not an access gate to safe existing module reads. Keep dashboard/navigation available and show a nonblocking owner/admin Finish setup action. Preserve existing module write contracts rather than inventing a blanket write freeze. Dispatcher sees approved operational fields and an owner-action notice; technician/viewer see only workspace/capabilities and no sensitive setup detail. Demotion/removal must stop configuration/replay reads and mutations. Do not conceal missing membership behind a setup page.

## Required decisions and precise clarifications

1. **First access:** publish the actual approved account/bootstrap and invitation delivery route, issuer matrix, expiry/canonicalization and safe recipient-error flow. A contract requiring an already verified Auth account does not by itself implement account creation. No clients may be asked to create database users, paste tokens into chat or edit configuration files. External invitation email remains separately scoped and authorized.
2. **Completion and draft saves:** Morgan accepts required fields/services/contact methods, seven-day schedule and all-closed handling. Atlas must reconcile schema bounds with Save incomplete semantics: business_contact_name and escalation names currently have nonempty limits while incomplete contact steps are promised. Specify which blank fields are storable/null versus only locally unsaved, separate draft validation from completion checks, and never show Saved for rejected data. Empty collections must remain incomplete, not defaults.
3. **Exact form/error/read shapes:** step model lacks concrete saved aggregate fields, missing_codes and next-action vocabulary; payloads and expected aggregate/config version relation need exact schemas before UI implementation. Publish safe field/index paths for services, intervals, exceptions and contacts, plus supported timezone choices and clear limit feedback. errors must map to a specific row/day/interval without echoing sensitive payloads. Define permissions/editable semantics rather than UI inferring them.
4. **Hours and rules:** an accessible seven-day editor with explicit Closed/Open and interval rows is feasible. Explain split overnight periods and that dated exceptions replace weekly hours. Show 24:00 as end-of-day only where allowed; do not shift dates silently. Null lead/buffer/horizon values mean Not configured, not zero; do not preselect universal60-minute service duration. Requiredness, all-closed review handling and capacity/escalation policy remain decisions, not UI defaults.
5. **Readiness freshness/recovery:** publish safe messages for each missing/error/check code and which actor can repair it. Invalid configuration cannot be mistaken for provider failure or empty success. Fetch errors preserve saved/editing context and offer retry; configuration conflict preserves local edits for explicit review, not auto-overwrite. After changed config, stale evidence must not stay verified. Readiness generated_at is informational and requires a reviewed refresh policy; this contract does not promise ongoing monitoring.

These limitations do not reject the proposed role separation or nonblocking setup design; they prevent implementers guessing policy or validation details.
