- **Database changes:**
  - Added private, RLS-enabled `reactivation_private.campaign_command_receipts`. No `anon` or `authenticated` table access is granted. `(tenant_id, request_id)` is the retry key; SHA-256 covers contract version, authenticated actor, and normalized input. Same-actor/same-input replay returns the prior campaign; actor or payload reuse returns a non-leaking conflict.
  - Added paired, finite `reviewed_by/reviewed_at` and `scheduled_by/scheduled_at` attribution columns to candidates. Actor values are derived from authoritative Auth identity and are never accepted from input.
  - Replaced broad tenant-member read policies with office-only policies for owner/admin/dispatcher. Viewer, technician, anonymous, unconfirmed/deleted, and cross-tenant identities receive no rows.
  - Revoked direct `INSERT`, `UPDATE`, and `DELETE` privileges from public API roles for campaigns and candidates. Candidate tenant/campaign/customer/lead links and all statuses are therefore immutable through direct Data API writes.
  - Added `has_reactivation_office_access(uuid)`, backed by the existing confirmed/non-deleted identity function and tenant membership. It is PostgreSQL-owned, `SECURITY DEFINER`, fixed `search_path`, revoked from `PUBLIC`/`anon`, and explicitly executable only by `authenticated`.
  - Added PostgreSQL-owned, fixed-search-path RPCs `create_reactivation_campaign(jsonb)` and `review_reactivation_candidate(jsonb)`, with explicit authenticated-only execution. Replaced `schedule_reactivation_visit(uuid,uuid,date,timestamptz,timestamptz)` without changing its signature and with the same explicit execution boundary.
  - Campaign creation, all candidates, initial campaign review state, audit triggers, and the receipt commit in one transaction. Scheduling locks the approved candidate and commits the internal job, internal appointment, booked status, scheduler attribution, and audit rows in one transaction. No email, SMS, weather, provider, external calendar, payment, automatic booking, or dispatch side effect was added.
- **API or contract changes:**
  - **Required 167L create adapter:** keep the existing server-side office-role authorization and history/draft generation, but replace every direct campaign/candidate insert and campaign status update with one `client.rpc('create_reactivation_campaign', { input })`. `input` must be exactly `{ tenant_id, request_id, name, season, channel, trigger_type, weather_trigger, candidates }`. Each candidate must be exactly `{ customer_id, lead_id, last_service_at, reason, subject, message }`. The existing page already supplies hidden `request_id`; 167L must validate that UUID directly from `FormData` and reuse it rather than generating a replacement inside the action. Do not send tenant/status/channel/creator fields per candidate; the database derives tenant, campaign, channel, status, and creator.
  - Create result states are `saved` or `replayed` with `campaign_id`, `campaign_status`, and `candidate_count`, or `conflict` with `reason: request_reuse`. SQLSTATE `42501` is unavailable/denied and `22023` is invalid input. Missing migration/function codes must retain the existing safe setup message. Never fall back to direct writes.
  - **Required 167L candidate adapter:** approve/dismiss must call `client.rpc('review_reactivation_candidate', { input: { tenant_id, candidate_id, decision } })`, where `decision` is only `approve` or `dismiss`. Success is `{ status: 'saved', candidate_id, candidate_status }`. The database permits `draft -> approved`, `draft -> dismissed`, and `approved -> dismissed`; all other transitions fail with SQLSTATE `42501`. Do not send reviewer, role, status, job, or appointment values.
  - **Required 167L scheduling adapter:** keep the existing RPC name and parameter names: `{ target_tenant, target_candidate, target_date, target_starts_at, target_ends_at }`. The database permits only an office member scheduling an `approved` candidate for a future, positive-duration visit of at most 24 hours. Success still returns `job_id` and `appointment_id`; retrying a booked/dismissed candidate fails closed. No external calendar write occurs.
  - Direct office-role reads may remain tenant-filtered `.select()` calls after `requireMembership(tenantId, OFFICE_ROLES)`; RLS independently enforces the same owner/admin/dispatcher boundary. Newly added attribution fields do not need a shared TypeScript contract change unless the UI later displays them.
