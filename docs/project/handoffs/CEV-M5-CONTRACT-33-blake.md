## Backend fit and conditions before implementation

1. **Tenant and role boundaries — fit.** Required customer and optional job/location chains use tenant-aware constraints and stable parents. Office-only draft/follow-up SELECT plus explicitly authorized commands conservatively avoids inheriting financial visibility from general CRM. Server verifies Auth/member/approved role; database independently enforces the same authority. Deferred lead/equipment/assignee inputs should explicitly reject rather than be silently interpreted as supported links.
2. **Transactional RPC — fit, owner/grants unresolved.** Ordinary session client calls only narrow reviewed commands, not service-role access. Revoke direct mutation privileges to prevent bypass of expectedVersion, receipts and aggregate rules. If definer RPC is necessary, RLS does not automatically protect its writes: each function independently verifies auth.uid/current tenant membership/role, scopes every lookup/write, derives actor, pins search_path, qualifies objects and revokes default PUBLIC/anon execute. Locking, membership-change behavior, exact execution owner/grants and audit-trigger compatibility need Atlas/Quinn approval and direct RPC tests. No generic mutation gateway.
3. **Replay contract — conditional on one concrete guarantee.** Current proposal leaves receipts optional; choose durable replay for all promised commands or explicitly specify conflict-safe at-most-once edits before coding. If replayed is part of each result contract, persist receipts atomically with business/audit changes. Reauthorize BEFORE any receipt read; require command/actor/tenant/request/target and canonical validated input binding. Define exact canonicalization including normalized whitespace/date/optional values and expectedVersion. A digest is not anonymization; private receipts must remain inaccessible and retain no raw scope/note payload. Creation's tenant-scoped submission uniqueness is additional to actor-scoped receipt uniqueness: a different actor's same token cannot create another draft, nor expose another actor's private receipt. Decide safe replay-versus-conflict behavior for that case.
4. **Concurrent duplicate/receipt race — implementation requirement.** Reserve or serialize operation identity within the transaction, compare digest and target, and return the original committed minimal result for identical retries. Changed payload under the same key returns request conflict. Handle simultaneous unique collisions without committing partial business changes/audits; use reviewed database transaction semantics rather than app-side sequential writes. Receipt lookup must precede stale-version rejection for an authorized identical lost-response retry; otherwise a successful prior edit incorrectly becomes revision conflict. Replayed version may be older than current version and must be labelled original receipt, not current content. Retention/expiry policy must not silently reset promised idempotency.
5. **Optimistic versions/lock ordering — fit.** Verify positive bounded expectedVersion, lock the current target under the approved parent-first order, check version/state, update once and increment atomically. Align receipt-lock and business-row lock order across all commands; specifying parent-first alone does not prevent receipt/row inversions. Estimate and follow-up versions remain separate. A version is not an issued immutable financial snapshot. Clarify CreateFollowup's parent precondition versus target version; if parent version required, publish exact field semantics rather than conflating follow-up and draft revision. Removed/denied parents remain unavailable, not foreign-record detail.

Competing create, reschedule/complete and repeated cancel need atomic state/version/receipt rules. Complete derives verified actor/server time; cancel preserves history without implying completed. Completed/cancelled edits/reopen must reject; a new manual task uses a new token. No assignee, scheduler, external send, job status change or appointment side effect implied. Morgan must accept one-active/unassigned/date-only recommendations first.

Result categories fit safe UI behavior; enumerate revision/request/active-followup conflicts in stable non-sensitive codes before implementation. Unknown database/provider details must not escape; preserve Next control flow and revalidate only committed success. If commit succeeded but response was lost, durable replay must recover it rather than duplicate.
