## Security design findings and required decisions

1. Authorization: Approve only an explicitly recorded office-only matrix; deny technician/viewer/anon all draft/follow-up content, not merely money columns or mutation buttons. Titles, scope notes and follow-up notes can contain sensitive financial/customer information. Require verified user and current membership/role for reads, commands and receipt replay. Revoke direct table writes if they bypass aggregate/version/state guards. Test exposed REST/RPC/views independently of UI. No ordinary service-role client.
2. RPC/RLS: Every exposed table needs explicit grants and RLS. SECURITY DEFINER may run with an owner capable of bypassing RLS; it must independently enforce authenticated subject, current role, tenant, parent, target and state constraints. Empty search_path, qualified objects, tightly controlled owner and no PUBLIC/anon execute are required. Audit function compatibility and any helper/view privileges require review before SQL. RLS alone is not a definer authorization proof. [Supabase functions](https://supabase.com/docs/guides/database/functions), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
3. Parent safety: Tenant-aware estimate/child FKs and immutable links are supported. Same-tenant alone is insufficient: selected job/customer/location must agree; customerless jobs reject under recommended anchor. Defer independent lead/equipment references as proposed; reject unexpected fields rather than silently retaining them. Lead customer changes must not rewrite a draft recipient; future equipment linkage needs exact location chain. Parent validation and locks must remain valid at commit. No estimate/follow-up command silently mutates CRM, jobs, lead dates or appointments.
4. Receipt privacy/idempotency: Decide exact replay guarantee before implementation. Private receipts need authorization before lookup/response and tenant/actor/command/target binding. Global tenant creation-token uniqueness cannot be bypassed with a different actor. Same token plus changed canonical input conflicts rather than overwrites; distinguish validated semantic values, omitted/null fields and expected version consistently. A digest is not anonymization: guessable low-entropy notes/amounts may be inferred from accessible hashes. Keep digests/results private, never log them, and review canonicalization, retention, expiry and replay-after-pruning behavior. Minimal original id/version replay must not disclose newest content or stale privileges. No raw PII/notes/line payload in receipts.
5. Audit/history: Atomic business/receipt/audit commit and no duplicate audit on replay required. Metadata-only audit rows and safe errors must not include scope/notes/prices/customer details or canonical hashes. Existing INSERT/UPDATE audit labels cannot claim semantic completion history by themselves. New entity audit visibility needs explicit review: existing generic audit access or search/dashboard joins must not expose draft details or existence to denied roles. Account removal must preserve business history under reviewed nullable actor policy; no destructive cascade.
6. Manual date semantics: Proposed strict date-only due_on is reasonable only after owner confirmation. Validate tenant timezone at trusted server boundary; invalid values fail safely without UTC/browser fallback. Due/overdue computed only for scheduled rows, current trusted workspace date; completed/cancelled immutable/history retained. Test midnight/DST and timezone changes without changing stored due_on. Date-only tasks never create a scheduler, message or calendar appointment. One-active follow-up, no assignee and terminal-state rules remain recorded decisions before implementation.
7. Scope/financial blockers: Currency/amount/quantity/unit/rounding/tax and financial-role permissions unresolved. No zero/missing-price or tax-free defaults; no accepted/sent/paid state, external sending, customer acceptance/e-signature, payment/financing, automated reminders, provider writers or recovered-revenue claim.
