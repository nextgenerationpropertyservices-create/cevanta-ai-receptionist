## One sequence for all six commands

Use READ COMMITTED transactions. A fresh SQL statement/snapshot after waiting on a membership or request advisory lock must see the committed role/receipt; do not cache a pre-wait membership/receipt snapshot. Repeatable-read/serializable execution is not silently equivalent: if later adopted, review serialization retry and membership visibility separately.

1. **Current identity and basic shape.** Server verifies getUser/current membership/office role before RPC. Inside RPC independently obtain auth.uid(); reject null. Validate strict command input shape and canonical types sufficiently to identify tenant/request/command/targets and compute final34 normalized-input digest. Unknown/protected fields reject; nothing is fetched from receipts or foreign records yet. Input parsing must never return stored content. No payload actor/role authority.
2. **Membership lock and role check.** Select `(tenant_id=input.tenant_id,user_id=auth.uid())` FOR SHARE and check the locked current role is owner/admin/dispatcher. Missing/non-office membership returns unavailable. This step runs for every new call and replay. Existing tokens are not authority. Revocation committed before lock check denies; transactions holding the membership lock may finish before later revocation commits.
3. **Tenant row lock, always.** Select this authorized tenant FOR SHARE; absence returns unavailable. Acquire this lock for every command including replay, before any advisory lock, and hold to transaction end. Read timezone but DO NOT validate it yet. Locking an invalid configured zone is not using it as a valid date authority. This removes the final34 conditional tenant-lock wording and prevents taking tenant locks after request/draft locks on either branch.
4. **Request advisory lock, always.** Obtain the transaction advisory lock for domain-tagged canonical `(tenant,actor,command,request_id)` using final34 encoding/hash rule. Holding it serializes identical requests until transaction commit/rollback. No mutation/receipt domain decision before this lock.
5. **Submission advisory lock, creates only.** DraftCreate and FollowupCreate then obtain the separate transaction advisory lock for `(tenant,entity-kind,submission_id)`, in that order after request lock. Existing-target commands have no submission lock. Both locks are obtained even when a receipt may exist; no receipt-driven late acquisition. Never reverse these two orders or acquire a second request/submission token inside one command.
6. **Private receipt lookup.** Read only exact `(tenant,actor,command,request_id)` after locks, using a fresh statement. No receipt row UPDATE lock is needed: committed receipts are immutable and request lock protects creation. Receipt exists: compare canonical digest AND command-specific target binding described below. A different digest/target returns request_reuse with no original target/content/result leaked. Only a matching receipt may enter replay authorization. No receipt exists: enter new-work target checks; token collisions are checked later as specified, not used to bypass target authorization.
7. **Current target authorization and row locks.** On either branch explicitly qualify every target by tenant and verify its required parent relationship. Lock draft FOR UPDATE, then follow-up FOR UPDATE if relevant. Use current office guard from step2 plus current scoped row existence; definer owner does not rely on RLS to provide these predicates. No broad receipt-result SELECT or cross-tenant ID lookup. Creation replay identifies target from the matched receipt under rules below; new DraftCreate has no draft row to lock and instead locks customer/job/location in that fixed order FOR KEY SHARE before creation. No replay acquires those creation-parent locks or performs new parent-choice validation.
8. **Branch.** Matching receipt plus valid current target bindings returns only replayed minimal original result. Otherwise new work applies domain checks, mutates/audits/inserts receipt and commits atomically. Hold earlier membership/tenant/advisory/target locks until transaction end. No domain failure creates a receipt; infrastructure/audit/receipt failure aborts all writes. RPC success is visible to the server only after transaction commit.

Global order therefore is membership → tenant → request-advisory → optional submission-advisory → draft OR draft-create customer/job/location → follow-up → business/audit/receipt writes. Replay changes which target is found, never lock order. Do not acquire tenant or membership locks again after aggregate locks. Constraint/audit helpers must not introduce reverse target/advisory locks; inventory actual trigger locks in implementation review.

## Exact receipt target bindings

Receipt `target_id`, `result_id` and input digest jointly bind the command. Digest includes all normalized arguments, contract version and expected versions exactly as final34; never derive it from mutable current content.

| scope_draft_create | target_id=result_id=new draft UUID; digest binds tenant, request, submission, requested customer/job/location and text | Lock receipt result draft in tenant; require its id=target_id=result_id and submission_id=input.submission_id. Compare immutable requested customer/job with draft; for location omitted at creation, allow the recorded derived location without re-deriving it. Original digest binds exact request; do not reinterpret omitted input against current job. Return draft_id=result_id. |
| scope_draft_update | target_id=result_id=input.draft_id | Lock input draft in tenant; require stored target/result match input. No other estimate target may satisfy the receipt. Return draft_id=input.draft_id. |
| scope_followup_create | target_id=input.draft_id; result_id=new follow-up UUID | Lock input draft in tenant, then receipt result follow-up in same tenant; require follow-up.draft_id=target_id=input.draft_id and follow-up.submission_id=input.submission_id. Return draft_id=input.draft_id. |
| scope_followup_reschedule | target_id=input.followup_id; result_id=input.followup_id; digest also binds input.draft_id | Lock input draft, then input follow-up in tenant; require follow-up.draft_id=input.draft_id and receipt target/result equal follow-up ID. |

| scope_followup_cancel | Same binding as reschedule | Same current draft/follow-up relationship and receipt binding checks. |

Result `entity` is derived from the exact allowed command, not client input. Receipt result_version must be positive, correspond to entity type and not exceed current target version; corrupt/contradictory private receipt produces generic retryable_failure with no private details and no replay/mutation, plus redacted operational investigation. A matching receipt with missing/inaccessible result or parent returns unavailable, never prior result as if it were current access. Do not expose whether an inaccessible target/receipt ever existed.

Current target authorization means current tenant office permission plus scoped draft/follow-up existence and immutable parent identity. It is not current expectedVersion or current business state. Normal draft/follow-up deletion/reparenting is prohibited by final34; trusted administrative corruption/removal does not grant replay permission. Do not look up or divulge other actors' receipts to infer creation ownership.

## New-work checks after receipt miss

- **Draft create:** after ordered customer/job/location locks and authorized same-tenant existence/chain checks, inspect `(tenant,submission_id)`. Any existing creation under a different request/actor is submission_reuse, without its ID/content. No draft-version precondition exists. Validate title/scope and derive job location as final34. Draft mutation does not require valid workspace timezone; tenant still locked at step3. Insert draft/version1 plus atomic audit/receipt.
- **Draft update:** after scoped draft lock, compare expected_version and exhaustion limit; permit only title/scope edits and increment once. No timezone-dependent domain rule. Identity/parents remain immutable.
- **Follow-up create:** lock scoped draft first; inspect submission-token reuse without exposing colliding row ID/parent. Then validate current tenant timezone, expected_draft_version, due date/note and absence of scheduled active follow-up. One-active unique index is final enforcement; draft lock serializes all follow-up mutations. Insert scheduled/version1 plus audit/receipt.
- **Reschedule/complete/cancel:** lock scoped draft then matching follow-up. Validate current tenant timezone only for this new mutation; require scheduled current state, matching expected_version and room to increment. Reschedule validates due_on/note; terminal commands derive actor/time. Terminal rows cannot be reopened or edited. Write once plus audit/receipt.
- The sequence of these safe failures is fixed: target unavailable first; for creates submission_reuse next; follow-up workspace_timezone_invalid next; expected-version/exhaustion conflict next; then state/active/date/text domain checks. Shape/lexical errors can be reported at step1 without looking up stored data. Do not report a foreign record's label/content or original version in any error.

## Replay checks retained versus skipped

Always retain: fresh authenticated subject/current office membership and membership lock; tenant existence/lock; strict input shape/canonical digest; request/submission lock order; exact actor/tenant/command/request receipt scoping; input/target binding; current target/parent visibility under office authorization; integrity of private receipt minimal result. Removed/demoted actors are denied even after a previous successful command. A different current authorized actor cannot replay another actor's result using its token; create collision is submission_reuse.

Skip on a matched authorized replay: timezone validity/configuration check, current expected-version equality, current version exhaustion, scheduled/terminal/active-count state, new due-date/relative-label interpretation, new customer/job/location selection derivation and content recalculation. Lexical validity of canonical original input is still required. This recovers a lost response even after later edits, completion/cancellation, a replacement active follow-up, or an invalid timezone setting. No business/audit/receipt write or timestamp refresh occurs. A replayed completion remains success from the original operation rather than terminal_followup conflict; a new request to complete a terminal row conflicts.

Return only final34 `{status:'replayed',entity,id,version,draft_id}` with original committed receipt version. It is not refreshed detail or proof the current row retains that earlier content/state. Server/UI obtain a separate currently authorized read for current detail/date labels; invalid timezone may make that read configuration_error without invalidating already committed replay. All errors remain final34 categories. No receipt digest, canonical input, note, title, private actor history or cross-tenant content in replay response/logs.
