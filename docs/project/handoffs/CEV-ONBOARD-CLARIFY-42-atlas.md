## Acceptance transaction and cross-module lock protocol

READ COMMITTED; fresh statements after lock waits. Universal provisioning/membership identity advisory key is `(domain:'membership-v1',tenant_id,target_user_id)`; all assigned invitation/provisioning/role-change/removal paths must take it BEFORE membership rows. Existing config/M5 commands do not wait on that advisory key, so adding this preceding administrative lock does not create a reciprocal dependency. Advisory collisions serialize, never supply identity.

Acceptance sequence: bounded token validation → verified Auth actor row FOR SHARE → preliminary private digest lookup solely to identify tenant/invite (no response yet) → target identity advisory lock → existing target membership FOR SHARE (absence protected by advisory and unique tenant/user key) → tenant FOR SHARE → acceptance request advisory `(tenant,actor,'invite_accept',request)` → invitation row FOR UPDATE → reread receipt and invitation under fresh snapshots → current identity/membership/invite binding checks → new work or authorized replay. The preliminary digest lookup is not authorization; recheck exact invitation ID/digest/tenant/recipient and terminal state under locks. No late tenant/membership lock. Unknown token returns unavailable without private names. Auth row locks precede database membership locks in all provisioning paths that touch Auth; no new path locks Auth after tenant/invite/job rows.

Trusted revoke uses target identity advisory → current target membership FOR SHARE if present → tenant FOR SHARE → platform request advisory → invitation FOR UPDATE, never writes membership. Trusted issue uses same order and recipient Auth-row-first when touching Auth, then serializes pending invite constraints. Role-change/removal uses identity advisory → membership FOR UPDATE → tenant FOR SHARE → dependent rows through existing cleanup triggers; it does not lock invitations after dependent business rows. Config/M5 keep membership → tenant → request → aggregate/children per their accepted contracts. No path holding tenant locks may newly acquire membership locks. Actual membership cleanup/FK/Auth-cascade locks must be inventoried by Blake/Quinn before implementing administrative RPCs; unrestricted manual SQL/Auth deletion is outside this cooperative protocol and cannot be claimed deadlock-free. Retry whole aborted transaction with original request on deadlock/serialization failure, never partial replay or role relaxation.

Acceptance receipts in private namespace onboarding-v1/invite_accept bind tenant+actor+request+token digest; target/result is invitation ID with accepted_user_id=actor and intended role. Receipt read occurs only after current authoritative user/email binding and invite row locks. Matching accepted retry SKIPS expiry but requires current exact intended-role membership, same actor, same invitation/token/email binding and not revoked; changed account email returns unavailable. No accepted replay creates/recreates membership or resets invite. If same invite accepted by same actor under a NEW request, current binding/membership still checked and returns already_accepted without new business/audit transition; optional new receipt records the minimal stable accepted outcome, not a second acceptance. Unknown actor/token never sees it. Pending expiry check uses trusted database clock AFTER waits, not transaction-start time. Request reused with another token conflicts generically; malformed input fails before receipt use.

Absent membership INSERT relies on existing unique tenant/user key plus advisory serialization. A collision from a noncooperating writer is handled by rereading current membership in a fresh statement: identical role can continue, differing role returns membership_conflict, no overwrite. Revocation/removal committed before locked guard denies replay. Prior authorized transaction may finish before a later removal commits; no retroactive cancellation guarantee. Invite acceptance, membership creation, metadata audit and receipt commit together; failure rolls all back.
