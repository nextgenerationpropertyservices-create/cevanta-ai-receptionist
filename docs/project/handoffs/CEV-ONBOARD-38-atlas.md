## Trust and role matrix

Existing tenants are provisioned by a trusted platform operator; first owner receives a scoped invitation. No public tenant create/claim, no tenant selection by email domain and no ordinary direct membership INSERT/UPDATE. This platform bootstrap is distinct from client setup: after entry the owner saves ordinary business configuration through protected app commands, not SQL/env/provider config files.

Owner/admin read and configure business profile, services, hours, booking preferences, escalation contacts and onboarding state. Dispatcher gets a limited operational read projection of services/hours/timezone/request rules only; no invitation management, sensitive recipient details, secret references or readiness diagnostic internals. Technician/viewer receive workspace identity and module capabilities only; no onboarding configuration access. All roles retain existing module permissions, including assigned-only technician jobs/appointments and M5 office-only drafts. Removed/nonmembers get unavailable. Configuration being incomplete must not grant permission or block an authorized user's safe read of already available modules.

Proposed invitation creation/revocation is owner-only for staff roles admin/dispatcher/technician/viewer, no owner role escalation. Initial owner invitation/ownership changes are trusted platform provisioning only, separately reviewed. Existing admin settings authority is not implicitly invitation/ownership authority. ## Proposed schema and invariants

Every public business table includes UUID id (or tenant singleton PK), tenant_id, positive integer version, created/updated timestamp and derived actor UUIDs. Composite unique/FK tenant relationships, explicit RLS and grants apply. Actor history is opaque and retained without Auth-user delete cascades; identifiers/parent/tenant/generated fields immutable. Text limits count Unicode code points; trim ASCII edge whitespace identically in SQL/server, reject NUL/invalid text. No freeform secrets/provider payloads accepted in any field.

**Private invitations:** id UUID, tenant_id, recipient verified-email binding, role app_role, token_digest bytea32, status pending/accepted/revoked, expires_at timestamptz, created_by/at, accepted_by/at nullable, revoked_by/at nullable, version integer, creation request ID and delivery status not_requested/pending/confirmed/failed/unknown. Expiry is derived from trusted now, not a fourth mutable status. Terminal states immutable; token hash unique; recipient binding not editable after creation. Token is cryptographically random256 bits, original available only for approved delivery, never logs/list/detail/storage as plaintext. Proposed lifetime48h is an engineering recommendation requiring explicit acceptance; use no configured expiry fallback. Private invitation read is narrow owner projection or acceptance-by-token RPC, not broad table SELECT. A delivery attempt/outbox contains encrypted token material only if a later approved provider design needs it; no unencrypted link in audit/history.

**public.tenant_business_profiles (tenant singleton):** display_name1–160, trade1–80, business_contact_name1–160, business_email nullable validated length254, business_phone nullable1–40, timezone IANA string, version and metadata. Draft setup can save incomplete contact fields; readiness requiredness is separate. Existing tenants.name/trade/timezone are compatibility authority until one reviewed migration explicitly chooses profile versus tenant source. Recommended keep these three in tenants and profile stores contact fields only; commands atomically update both under tenant lock and shared config revision. No duplicate writable timezone. No currency, address jurisdiction, tax or legal fields inferred.

**tenant_services:** id/tenant, name1–120, description0–2000, enabled Boolean, position integer0..9999, version/metadata; unique tenant/id and tenant/position among enabled records or deterministic position/id ordering. No price, universal duration or automatic bookability. Service names need not be unique unless product chooses that constraint; IDs identify services. Disabling preserves references/history.

**tenant_hours_days:** tenant/day-of-week0..6 (ISO Monday0), explicitly closed Boolean; unique tenant/day. **tenant_hours_intervals:** id/tenant/day FK, starts_minute integer0..1439, ends_minute integer1..1440, starts<ends, unique tenant/day/start/end; prevent overlap for each day. Closed day has zero intervals; open day has at least one. Replace entire weekly schedule atomically with all seven explicit days; no automatic weekdays/open hours. **tenant_hours_exceptions:** id/tenant, local_date finite year0001..9999, closed Boolean, unique tenant/date; interval children mirror day bounds/overlap. An exception fully replaces weekly hours on that date. Overnight intervals split into separate dates/day entries; UI must explain, never silently shift. Closed overrides cannot contain intervals. Exceptions retained until reviewed cleanup; no calendar writer.

**tenant_booking_preferences (tenant singleton):** internal mode literal request_only, enabled_service references through tenant-safe join if restrictions needed, optional lead_time_minutes0..525600, buffer_before_minutes/buffer_after_minutes0..1440, horizon_days1..730 and notes0..2000. Values nullable mean not configured, never zero/default policy. These are saved proposed operational preferences only; do not enforce availability or enable live booking. Approved60-minute validator scope remains separate; per-service duration/capacity/resource policies require explicit owner decisions and new contracts. UI must label request-only/manual review, not appointment reservation.

**tenant_escalation_contacts:** id/tenant, label1–120, contact_name1–160, optional email<=254/phone<=40, enabled Boolean, position0..9999, version/metadata. Require at least one syntactically valid selected contact method for a complete record, but saving an incomplete step is allowed via explicit draft validation. No automatically verified destination, emergency recipient, urgency timeout, after-hours routing or transfer policy. Verification evidence follows separate authorized actions; contact presence is not delivery/acknowledgment. Sensitive details owner/admin only.

**tenant_setup_state:** tenant singleton, flow_version literal onboarding-v1, config_revision integer positive, version positive, last_changed_at; **tenant_setup_resume:** tenant/user PK, step_id from access/profile/services/hours/booking/escalation/integrations/review, version, updated_at. Resume belongs to current member and carries no completion authority; config completion derives from saved data. Shared config_revision increments once for each changed setup aggregate, never on navigation or exact replay.

**Private readiness evidence:** tenant/id, module/code, config_revision, outcome verified/failed, checked_at, expires_at nullable under versioned check policy, check_version, evidence_source automated/operator_observed, restricted actor/reference, safe failure code. No raw logs/payloads/keys; only trusted checker/operator can create evidence. An unknown expiry/check policy cannot produce verified. Provider connection references/routes/secrets are not introduced through these tables; later reviewed secure connection store required.

Indexes: tenant/service enabled+position; hours tenant/day and exception tenant/date; escalation tenant/enabled+position; resume tenant/user; readiness tenant/module/config_revision/checked_at; invitation digest unique and tenant/status/expiry. Grants/constraints/indexes land in one additive reviewed migration, not modifications to applied foundations.

## Invitation acceptance contract

`AcceptInvitation({request_id:UUID, token:string})` only; no tenant/role/email/user arguments accepted. Limit token format/length before processing; derive actor from verified Auth getUser and auth.uid(), verified confirmed account email obtained from trusted Auth state, not user_metadata/body. Lock invitation identified by digest, verify not revoked/expired and exact recipient binding with reviewed email canonicalization; no Gmail-dot/plus normalization. Initial account-password/email verification flow must complete through reviewed Auth mechanisms before membership mutation. Token possession alone never authenticates a user or overrides recipient email.

Single transaction checks tenant existence, pending invite validity and intended role, locks existing membership if present, creates membership if absent and marks invite accepted. Existing membership of identical role accepts without duplication; differing role returns membership_conflict without altering role. Accepted same actor can re-enter via identical token while currently a matching allowed member; revoked/demoted/removed member cannot recreate membership from an accepted invitation. Expired accepted token does not grant login: authenticated existing member uses normal workspace entry, not token reacceptance. Cross-actor acceptance always generic unavailable. Revoke and accept serialize on invitation row; no partially accepted membership/audit result.

Success `{status:'accepted'|'already_accepted',workspace:{id,name},role,entry:'setup'|'dashboard'}` only after commit. Failure `{status:'unavailable'|'membership_conflict'|'retryable_failure'}`; before verified identity, Auth-required control flow instead of email/tenant enumeration. Do not reveal invalid versus wrong-recipient/expired tenant names. Owner management list exposes masked recipient/status/expiry only; authorized individual detail may reveal email, never token. Membership and private invite audits record IDs/action/actor/time only; do not use the existing generic audit trigger on tables without expected tenant/id fields unless adapted/reviewed.

Invitation delivery/account bootstrap remains separately authorized: this design does not send email, create Auth users using ordinary service credentials, reveal invitation links in chat, or choose a provider. A restricted privileged provisioning worker may be required for Auth administration; it must be independently assigned/reviewed with allowlisted actions and no ordinary app service-role path. Owner/admin tenant setup uses session-authorized commands after membership exists.

## Configuration commands, replay and read models

Commands: SaveBusinessProfile, ReplaceServices, ReplaceWeeklyHours, UpsertHoursException, RemoveHoursException, SaveBookingPreferences, ReplaceEscalationContacts, SaveResumeStep. Strict `{tenant_id,request_id,expected_version,payload}` objects; each payload contains only its named fields, bounded arrays (services<=100, intervals<=8/day, escalation<=20) and no money/provider/actor/status overrides. Explicit existing child UUIDs scoped to tenant; new IDs assigned in SQL. Replacements preserve existing IDs referenced elsewhere and disable rather than silently delete services/contacts with history. Empty collections are valid incomplete configuration, not automatic ready.

Use tenant-authorized owner/admin guards independently server+database, narrow transactional RPCs, expected aggregate/config version, atomic row/config-revision/audit/private receipt writes. Revoke direct business mutations and broad helper EXECUTE; public SELECT/RLS only for exact intended projections. Definer RPC owner, fixed empty search_path and explicit auth/tenant/role validation must be specified in actual migration review; no relying on RLS to protect elevated writes. Separate sensitive contacts/private invitations from generally readable tenants rows. Dispatcher projection provided through security-invoker authorized boundary, not a bypassing owner view.

Consistent configuration mutation lock order: current membership FOR SHARE/check → tenant FOR UPDATE → request advisory identity → aggregate parent → children sorted by UUID → audit/receipt. Resume uses same order, but permits only current user's own resume and never increments config revision. Avoid mixing onboarding invitation membership writes into M5/config locks: invitation provisioning lock-order/role-change interaction requires Blake/Quinn concrete SQL review before implementation. No speculative deadlock-free runtime claim.

Private durable receipts scoped tenant/actor/command/request bind canonical validated input/target digest and minimal original result, retain while business history retained; changed reuse conflicts. Current authorization and target access always checked before returning replay; original committed revision is not current content. Exact replay skips new version/configuration domain checks and makes no new audit/change. Any cross-command submission identity for provisioning needs separate unique constraints and conflict handling, not app-side lookup only.

Results: saved/replayed `{entity,id,version,config_revision}`; conflict `{code:revision|request_reuse|referenced_record}`; validation_error `{field,code:invalid_input|invalid_timezone|overlap|invalid_relationship}`; unavailable; retryable_failure. No payload echoes/SQL/private data. Server preserves input and revalidates after confirmed commit only. Onboarding acceptance retries cannot promote role or recreate revoked access.

`GetOnboarding(tenant)` owner/admin projection: workspace identity, permissions, config_revision, flow_version, resume_step, step models and readiness. Step model `{id,state:incomplete|complete|blocked|error,missing_codes:string[],editable:Boolean,version}`. Safe setup fields/forms contain saved business data only; secret inputs/routes excluded. Others receive `{workspace,capabilities,setup_action_required:Boolean}` without diagnostic details or sensitive contacts.

`GetReadiness(tenant)` authorized summary: `{generated_at,config_revision,configuration_state:incomplete|complete|invalid,manual_workspace_state:usable|blocked,integrations:[{module,state:unconfigured|awaiting_verification|verified|degraded|disabled,checked_at,expires_at,reason_codes}],booking_state:'blocked',release_state:'not_evaluated',next_actions:[{step_id,code,actor:owner|platform_operator}]}`. Verified only for matching current revision/evidence policy; expired evidence becomes awaiting_verification, never silently carries forward. No client SetReady or operational activation command.

## Validation/time/readiness semantics

Timezone is a validated supported IANA identifier at both database and server; no offset abbreviations or fallback to browser/UTC. Hours are local civil-time definitions, not timezone-less appointment instants. Exceptions use workspace local date; interval end1440 means next local midnight. Save timezone must invalidate affected readiness and bump config_revision atomically, preserving stored local schedule definitions and UTC existing appointment instants. DST nonexistent/ambiguous slot resolution and future reservation use a later reviewed booking contract; saved hours alone do not authorize booking.

Proposed configuration completion requirements for Morgan approval: profile display name/trade/valid timezone and one business contact method; at least one enabled named service; all seven explicitly valid hours days (all closed is allowed saved state but triggers review requirement for operational use); request-only preferences acknowledged/saved; at least one complete escalation contact. Integration step may be blocked pending platform checks and cannot be marked complete from a URL/token. Missing fields/invalid configuration are distinguished from provider infrastructure blockers. Because these requiredness rules are not owner-recorded, implementation must not silently enforce them as product policy before review/acceptance.

Readiness checks here are pure backend derivation, no provider calls, messages, bookings or contact verification effects. Manual workspace usable means authenticated membership + reachable protected module schema/workflows within evidence-defined scope; it is not whole product ready. Current AI/handoff/M5/reporting unavailable states remain truthful. Health/database-configured presence is not tenant readiness. Final production release readiness belongs to Morgan/Phoenix checklist, not tenant checkbox.
