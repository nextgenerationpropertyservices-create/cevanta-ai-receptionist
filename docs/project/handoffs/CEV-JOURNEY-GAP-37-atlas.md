## Recommended onboarding data/contract architecture

1. Preserve tenant/membership identity. Account bootstrap/invitation must validate intended verified recipient, single-use/expiry/replay, tenant/role authority and atomic membership creation without exposing ordinary role grants. Separate owner first-workspace creation from inviting staff; record who can do each and protect against claiming existing tenant/name/domain ownership. Owner-created workspace/provisioning invitation path is a material product decision for Morgan, not an inferred public signup endpoint. No service-role client in ordinary requests; any privileged Auth provisioning worker is separately reviewed and narrowly authorized.
2. Extend business configuration through tenant-scoped records: profile, service catalogue, weekly hours/exception dates, booking policy and escalation configuration. Use normalized relationships for repeated services/intervals/recipients, bounded fields and composite tenant foreign keys; avoid one unvalidated JSON blob as authority. Exact required fields, customer-facing contact visibility, service area, exception precedence, capacity and recipient policies need product/contract decisions. Sensitive escalation contact details are business data requiring restricted access/retention, never audit payloads.
3. Version configuration and mutations; save each step atomically with expected revision, tenant-scoped retry protection and metadata audit. New records need independent RLS/grants and operation-specific server checks. Recommend owner/admin configuration writes; dispatcher read/write subset requires explicit approval, technician/viewer must not inherit integration/recipient credentials/settings. Public or customer-facing business-profile projection, if required later, is a separate allowlist contract, not raw tenant/settings SELECT.
4. Persist minimal onboarding resume state `(tenant,flow_version,current_step,version,timestamps)` and optional explicit acknowledgments; derive actual completed/missing/error state from validated saved configuration and authorized verification records. Do not persist an independently mutable universal ready Boolean. Steps can be incomplete/complete/blocked/error with stable safe reason/action codes; permissions determine editable versus owner-action-required presentation.
5. Readiness separates **configuration complete**, **manual workspace usable**, **integration connected/verified**, **booking operational**, **release-approved**. A module can be unconfigured, configuration-valid, awaiting verification, verified, degraded or disabled. Report evidence source, checked_at, config revision and expiry; changed credentials/routes/services/hours revoke affected verification. Evidence must be produced by trusted checks or authorized recorded observations, never client-supplied success flags. Store no raw provider responses/secrets in readiness history. Internal dashboard may be usable while provider activation remains blocked; do not label that full receptionist readiness.
6. Time contracts distinguish business local hours/date-only exceptions/manual due dates from absolute UTC appointment instants. Centralize valid IANA timezone and trusted workspace date; handle unknown/invalid zone safely without browser/UTC defaults. Define ambiguous/nonexistent local appointment-time resolution before live booking. UTC manual calendar and owner-local onboarding display need an explicit compatibility conversion contract; do not silently reinterpret existing instants or dates when timezone settings change.
7. Integration configuration contains opaque connection references, authorized provider/account/agent bindings and status only. Secrets live in reviewed secure storage behind restricted backend operations; never ordinary tenant profile/browser projections. Connection checks require actual provider evidence under a separate authorized task; guided UI cannot bypass current host/admission/verifier/route/dedupe/availability gates.

## Shared dashboard/module contracts

Introduce a tenant/role-scoped summary boundary rather than assembling unrestricted record arrays in the browser. Response should declare authorized capabilities, workspace date/timezone, snapshot/generatedAt, configuration revision, readiness reasons and each module's own ready/unavailable/error state. Counts and recent items follow that module's RLS/current assignment rules; technician jobs/appointments remain currently assigned only and M5 remains office-only. No global count may leak records hidden in detail. Module failure must be visible as unavailable/error, not zero data or successful setup.

Customer/intake/job/calendar write results stay persistence-confirmed, with validated parent chains and server authorization; onboarding/profile changes must not alter record identities. AI activity/handoff needs independently reviewed tenant receipt/call/lead/handoff/outbox persistence and limited payload/retention. Manual handoff transitions require current authorized membership, actor/evidence and defined timeout/recovery policy.

No price/total/revenue widgets, receipt content or privileged audit expansion. Configuration timezone validation is a shared dependency, but moving validation ownership requires a documented transfer and compatibility tests, not edits to other agents' contracts here.

Reporting first requires an approved metric dictionary: source table/event, state filters, distinct entity key, tenant/role scope, time basis/window/timezone, freshness and incomplete-data behavior. Safe candidates for review are customer count, manual lead statuses, assigned job activity, appointment status and office pending/overdue follow-ups. These are operational counts, not revenue impact. Historical funnel conversion cannot be reconstructed honestly from current mutable statuses alone; if required, define retained transition evidence before making trend claims. Monetary/recovered-revenue reporting stays blocked on authoritative payment/revenue sources and attribution decisions.
