# Invitation continuation contract

Date: 2026-10-26  
Task: CEV-PROJECT-AUDIT-167P  
Status: architecture approved for implementation planning; no runtime or database change is included here

## 1. Decision

Cevanta invitation links must stop placing the invitation token in the query string. A newly issued link uses one fixed public entry path and a fragment payload:

`https://<configured-app-origin>/invite#v=1&r=<request UUID>&t=<43-character canonical base64url token>`

The fragment is never sent in an HTTP request. An early, same-origin bootstrap removes it with `history.replaceState` before rendering invitation content or starting any exchange. The bootstrap then sends the bounded payload once to a same-origin POST endpoint. The endpoint stores only cryptographic digests, creates a short-lived opaque continuation, and sets that continuation as an HttpOnly cookie. All later sign-in and acceptance steps use the opaque continuation; the raw invitation token never reaches React props, form fields, the database, local/session storage, analytics, logs, errors, or subsequent URLs.

This contract preserves the existing rule that an invitation can be accepted only by the exact confirmed, non-deleted Auth account named when the invitation was issued. The fragment is not authorization by itself.

## 2. Security boundaries

### Raw invitation token

- Remains 32 random bytes encoded as canonical, unpadded base64url (43 characters).
- Exists only in the operator's one-time copied link, the recipient browser's fragment, the bootstrap's short-lived local variable, and the exchange request body.
- Is decoded and SHA-256 hashed at the server boundary. Only the 32-byte digest is passed to PostgreSQL.
- Is never returned by the server and is never written to a cookie, URL query, response body, DOM, React state, form field, storage API, audit row, receipt, exception, or log.

### Opaque continuation

- Is a second independent 32-byte random value generated by the application server during exchange.
- Is stored in the browser only as an HttpOnly cookie and in PostgreSQL only as a SHA-256 digest.
- Carries no tenant, invitation, user, email, role, or provider identifier.
- Is valid for at most 15 minutes and never beyond the underlying invitation expiry.
- Is single-use for acceptance. A new successful exchange for the same pending invitation revokes the earlier unconsumed continuation.

### Verified identity

- Exchange may occur before sign-in, but an authenticated exchange from the wrong account fails generically.
- Acceptance requires `onboarding_private.current_identity()` to return the exact confirmed, non-deleted `recipient_user_id` and canonical email already stored on the invitation.
- Neither the URL, cookie, browser, server action, nor request body supplies the actor, tenant, role, or intended recipient.
- Existing membership conflict rules remain authoritative. Acceptance cannot upgrade or replace an existing different role.

## 3. Browser entry sequence

The `/invite` page is a dedicated no-index bootstrap surface.

1. The first executable page element is a small audited inline bootstrap. It must not depend on React hydration.
2. It reads `location.hash` into a local variable and immediately calls `history.replaceState(null, "", "/invite")` before rendering invitation content, importing optional code, registering analytics, or making an exchange request.
3. It accepts exactly the keys `v`, `r`, and `t`; requires `v=1`; validates the UUID and canonical token shape; rejects duplicates, extra keys, oversized fragments, percent-decoding failures, and noncanonical values.
4. It POSTs `{version:1, request_id, token}` as JSON to `/api/invitations/continuations` on the same origin. The body limit is 1 KiB and `Content-Type` must be `application/json`.
5. It clears its local payload variables after constructing the request. It never writes them to the DOM, state, storage, console, error reporting, or telemetry.
6. On a successful exchange, it uses `location.replace("/invite/continue")`. On any failure, it stays on the clean `/invite` URL and renders one generic recovery message: ask the Cevanta operator for a new private invitation.

The entry document and exchange response must use:

- `Cache-Control: private, no-store, max-age=0`
- `Pragma: no-cache`
- `Referrer-Policy: no-referrer`
- `X-Robots-Tag: noindex, nofollow, noarchive`
- a Content Security Policy that permits only required same-origin application assets and the audited inline bootstrap by nonce or hash; no third-party scripts, pixels, frames, or network destinations

The browser page must contain no analytics or third-party resources. Same-origin framework asset requests do not receive the fragment in HTTP, but the bootstrap still removes it before displaying invitation UI.

### Browser-history and screenshot limitation

`replaceState` replaces the current history entry, so normal Back/Forward history must not retain the fragment. Hosted browser tests must prove this. No web application can prevent a recipient, operating system, browser extension, or external camera from capturing the address bar before the first inline instruction executes. Therefore the enforceable guarantee is that Cevanta-controlled HTML, DOM, logging, analytics, automated evidence, and screenshots never contain the raw token after bootstrap begins. The operator must still send the original link only through an approved private channel. Claiming an absolute OS-level screenshot guarantee would be false.

## 4. Exchange endpoint

`POST /api/invitations/continuations` is the only token exchange endpoint.

It must:

- reject non-POST methods, cross-origin `Origin`, mismatched `Host`/forwarded host, non-JSON content, missing or excessive `Content-Length`, bodies over 1 KiB, extra keys, malformed UUIDs, and noncanonical tokens;
- accept only same-origin browser requests (`Sec-Fetch-Site: same-origin` or a specifically tested browser-compatible absence policy); never enable CORS;
- decode and hash the token in process memory, generate a fresh continuation value, hash it, and call the narrow database exchange command through an anonymous or authenticated public Supabase session—not a service-role client;
- return only `{status:"ready"}` or `{status:"unavailable"}`; database, invitation, tenant, email, user, role, token, digest, request, and expiry details are never returned;
- avoid application/provider payload logging and error reporting; operational metrics may record only an allowlisted category and HTTP status;
- set the continuation cookie only after the database confirms creation.

Cookie contract:

- name: `__Host-cevanta-invite`
- value: raw opaque continuation only
- `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, no `Domain`
- `Max-Age` no greater than 900 seconds; database expiry remains authoritative
- `Priority=High`

The `__Host-` prefix intentionally requires `Secure`, host-only scope, and `Path=/`. The broad path is needed so the fixed sign-in action can detect the pending continuation and return to `/invite/continue`; JavaScript cannot read it.

## 5. Database contract

### Private table

Add `onboarding_private.invitation_continuations` with:

- `id uuid primary key`
- `tenant_id uuid not null`
- `invitation_id uuid not null`
- `recipient_user_id uuid not null`
- `acceptance_request_id uuid not null`
- `handle_digest bytea not null unique`, exactly 32 bytes
- `created_at timestamptz not null`, finite
- `expires_at timestamptz not null`, finite, later than creation, no more than 15 minutes later, and no later than invitation expiry
- `consumed_at timestamptz null`, finite when present
- `revoked_at timestamptz null`, finite when present
- `version integer not null`, bounded and monotonic
- composite foreign key `(tenant_id, invitation_id)` to the existing invitation identity
- a foreign key or trigger assertion binding `recipient_user_id` and `acceptance_request_id` to that exact invitation
- a state check preventing both `consumed_at` and `revoked_at`
- one active-continuation-per-invitation enforcement (partial unique index or equivalent locked invariant)

The table has RLS enabled and no table privileges or policies for `anon`, `authenticated`, or `service_role`. Only fixed-search-path, PostgreSQL-owned security-definer commands may access it. Audit events may record creation/consumption by continuation row ID and actor where available, but never a raw token, raw handle, digest, email, cookie, request body, or URL.

### Public exchange command

Add a narrow function such as:

`public.exchange_invitation_continuation(input jsonb) -> jsonb`

Input is exact and bounded: `request_id`, `token_digest_hex`, `continuation_digest_hex`, and a server-computed expiry. Execution may be granted to `anon` and `authenticated`, but not `service_role`. It must:

1. Validate exact keys, types, 32-byte digests, and expiry bounds.
2. Resolve the invitation by both creation/acceptance request identity and token digest without returning whether either matched.
3. Require pending, unexpired, non-revoked invitation state and a live recipient identity. If an authenticated current identity exists, it must match the recipient.
4. Take the existing invitation/membership advisory lock, lock the invitation, revoke an earlier active continuation, and insert one new continuation atomically.
5. Return only `created`, `unavailable`, or `retryable_failure`. All invalid, missing, expired, revoked, wrong-account, and substituted inputs map to `unavailable`.

Do not add a lookup/read command that reveals invitation or continuation state.

### Authenticated acceptance command

Replace raw-token acceptance with:

`public.onboarding_accept_invitation_continuation(input jsonb) -> jsonb`

Input is exact and bounded: `continuation_digest_hex` only. The request identity is read from the locked continuation row. Execution is `authenticated` only. It must:

1. Derive the actor and canonical email from `current_identity()`.
2. Lock the continuation, require active/unexpired state, then take locks in the existing documented membership/invitation order.
3. Lock the exact invitation and require pending, unexpired, non-revoked state; exact tenant/invitation/recipient/request binding; actor ID and canonical email match; and intended-role compatibility.
4. Insert the membership, membership audit, invitation transition, invitation audit, existing acceptance receipt, and continuation consumption in one transaction.
5. Return the existing strict accepted workspace envelope only after all writes succeed.
6. On replay, concurrent loss, wrong account, expired/revoked/substituted handle, accepted invitation, removed membership, or missing row, return `unavailable` without recreating access. A consumed continuation can never recreate a removed membership.
7. Roll back every write if any audit, receipt, invitation, membership, or continuation write fails.

The old `public.onboarding_accept_invitation(jsonb)` raw-token command must lose `authenticated` execute permission in the continuation migration. It may be dropped in a later cleanup migration after hosted observation, but it must never be re-enabled as rollback.

## 6. Sign-in and acceptance flow

- `/invite/continue` reads only the HttpOnly continuation cookie on the server and never exposes its value.
- If signed out, the page links to the normal sign-in page. The successful sign-in action checks only whether the named continuation cookie exists and chooses the fixed destination `/invite/continue`; it does not accept a client-supplied return URL.
- Invitation issuance continues to require a pre-existing confirmed account. Do not add a sign-up shortcut that implies an unconfirmed/new account can accept the invitation.
- If signed in, the acceptance form contains no invitation ID, request ID, token, continuation, tenant ID, email, role, or return URL. The server action reads and hashes the cookie, calls the authenticated acceptance command, and clears the cookie before returning.
- Success redirects only to the strictly decoded workspace ID returned by the database, at `/workspaces/<UUID>/onboarding`.
- Failure clears the cookie and returns the same generic unavailable message. To retry, the recipient reopens the original private link; no error may distinguish missing, expired, revoked, wrong-account, replayed, or malformed state.

## 7. CSRF, concurrency, replay, and recovery

- `SameSite=Strict`, exact Origin/Host validation, no CORS, JSON-only exchange, Next.js same-origin server-action checks, and authenticated database identity form the CSRF boundary.
- Exchange and acceptance both use the existing membership/invitation advisory-lock order. Continuation row locking is added before invitation mutation without taking a later conflicting lock.
- Concurrent exchanges leave exactly one active continuation. Concurrent accepts produce exactly one successful atomic acceptance; all others receive `unavailable`.
- Network loss after exchange is safe: reopening the original link revokes the earlier unconsumed handle and issues one fresh continuation.
- Network loss after acceptance is safe: the membership remains accepted, but the consumed handle returns `unavailable`; the recipient enters through normal sign-in/workspace navigation.
- Revoking or expiring the underlying invitation invalidates every continuation immediately, regardless of cookie expiry.
- Removing membership after acceptance is final. Neither an accepted invitation nor a consumed continuation may recreate it.

## 10. Non-goals

This contract does not email invitations, create accounts, enable providers, complete onboarding, change readiness, activate automations, or weaken workspace authorization. It adds no service-role path and no client-readable invitation-status endpoint.
